# Evil Shao · Android 版

> 应用名（桌面图标、最近任务、设置里显示的名字）是 **Evil Shao**，
> 也就是「邪恶邵」的英文写法。包名 `com.unclema123.evilshao`。

屏幕上一只**真 3D** 的拟人小猪（OpenGL ES 2.0 渲染，不是贴图）。
拖动可以真的转到侧面和背面，点一下她会随口吐槽，打字说话她头顶冒气泡回你。

## 安装

```
app/build/outputs/apk/debug/app-debug.apk
```

把这个 APK 拖进雷电模拟器（或发到手机）即可安装。最低 Android 7.0（API 24）。

## 构建

```bash
gradle assembleDebug
```

需要：

- JDK 17 或 21
- Android SDK，含 `platforms;android-35` 和 `build-tools;35.0.0`
- `local.properties` 里指定 `sdk.dir`

## 实现要点

| 文件 | 作用 |
|---|---|
| `Mesh.kt` | 球体/圆柱体网格生成，position+normal 交错存放 |
| `PigRenderer.kt` | GLES20 渲染器：Phong 着色、深度测试、每帧动画 |
| `Quotes.kt` | 语录解析 + 关键词打分回复 |
| `MainActivity.kt` | 触摸拖拽旋转、气泡动画、输入框、记录面板 |
| `ChatLog.kt` | 聊天记录落盘（jsonl）与导出 |

几何体在构建时就把半径烘进顶点，运行时只做旋转和平移——这样法线矩阵等于旋转矩阵，
不需要求逆转置，也避免了非等比缩放把法线搞歪。

## 聊天记录

每次对话都会落盘，两个人说的话都记，右上角「记录 N」按钮可以翻看、分享、清空。

- 存放位置：`/data/data/com.unclema123.evilshao/files/chatlog.jsonl`
- 格式：每行一条 JSON，`{"t":时间戳,"r":"我"/"她","m":"内容"}`
- 记录内容：你发的每条消息、小猪的每条回复、以及点她脑袋触发的那句吐槽
- 显示按天分组，开头有 `你 N 条 · 她 M 条` 的统计
- 「分享」走系统分享面板，可以直接发到微信/QQ/邮箱

### 设置两个人的名字

- **第一次启动**会自动弹窗让你给自己起名字（可以「以后再说」）
- **之后随时**点左上角的标题改
- 机主名字和小猪名字都能改，最多 12 个字
- 文件里存的是角色代码（`我`/`她`），名字只在显示时替换，所以**改名后历史记录立刻跟着变**，不用回写文件
- 存在 `shared_prefs/names.xml`

用 adb 也可以直接读出来：

```bash
adb -s 127.0.0.1:5555 shell run-as com.unclema123.evilshao cat files/chatlog.jsonl
```

> **注意**：记录只存在本机上。别人在自己的手机上装了这个 APK，他们的聊天记录你这边看不到。
> 要让多个人的记录都汇总到你这儿，需要一个后端（服务器收数据），目前没有。

## 本地自学习（不联网、不部署）

她从聊天记录里自己琢磨「哪句话效果好」，然后改变以后挑哪句说。整个过程离线，数据不出手机。

**怎么判断好坏**（隐式反馈，不需要你点赞）：

| 你的下一条消息 | 判定 |
|---|---|
| 含「哈哈」「对」「厉害」「6」等 | 上一句 +1 赞 |
| 含「无语」「不对」「什么鬼」「??」等 | 上一句 -1 踩 |
| 把同一句话又问了一遍 | 上一句 -1（说明没答到点上） |
| 其他 | 无信号 |

**权重公式**：`w = (赞+2) / (赞+踩+4)`，拉普拉斯平滑，0.5 为中性。

**怎么影响回答**：候选回复按权重加权抽样，被夸过的更容易再出现，被嫌弃的被压低；
从没用过的句子给一点额外机会（探索），避免过早锁死。另外还带一点长度适配——
你说得长，她偏向长一点的回复。

**什么时候学**：启动时学一遍，之后每 12 条消息自动再学一遍。

**数据位置**：`files/learn.json`

```bash
adb -s 127.0.0.1:5555 shell run-as com.unclema123.evilshao cat files/learn.json
```

界面右上角「学习 N」按钮可以看到她学到的东西（分数最高的几句、被嫌弃的几句），
还能手动「学一次」或「重置」。

> **说明**：这是统计加权的强化学习，不是神经网络。她自己能造新句（见下一节），
> 但造出来的是**语法成立、风格一致**的句子，不是真的理解你的意思。

## 自己造新句子

她会在每轮自学时顺手造 2 句新的，用的是**她自己语言碎片的重组**，不是随机拼字。

**碎片来源**（全部摘自真实聊天记录）：

| 槽位 | 例子 |
|---|---|
| 开场 | 我的天、哎呀，我的妈呀、我去、窝趣、呵呵、噢、嗯、…… |
| 自夸 | 谁让我这么聪明、我这么人美心善、我家没我得散、我大度、这我拿手 |
| 怼人 | 你猜我是傻子吗？、反弹。、你可以闭嘴了、我允许你再猜一次、起开、瞎说 |
| 感叹 | 笑死我了、我真是服了、窝趣、对对对、哈哈哈 |
| 语气尾巴 | 吧、啊、呢、呗、哈、呀 |
| 头衔 | 德州市长、班长、团支书、学管会主席 |

**句式模板**：`开场，感叹` / `自夸+尾巴` / `怼人` / `开场，怼人` / `感叹。` /
`建议推举我当X` / `比起X，我更想当Y`

**风格校验**（不合格就丢弃重造）：

- 长度 3~24 字，一句里最多一个逗号
- 去掉标点后不能和已有句子重复（所以不会造出「笑死我了。」这种）
- 不能有英文字母/数字
- 不能出现连续三个相同字符

**造完怎么办**：新句进入候选池，和学习权重共用同一套评分。被夸的留下来并且更容易被说，
被嫌弃的权重自然掉下去——相当于自然选择。

实测样本：

```
窝趣，我真是服了          我的天，笑死了
我的天，反弹。            我就知道呗
这我拿手哈                我也是要面子的人吧
```

界面「学习」面板下半部分能看到她造的全部新句，还能点「再造几句」。

**数据位置**：`files/invent.json`

## 接入大模型（可选，默认关闭）

默认完全离线跑本地语料。想让她真正「听懂」你的话，可以接一个大模型。

**入口**：右上角「学习」→「接AI」→ 填接口地址、模型名、API Key → 保存 → 勾上「启用大模型」。

**免费方案**（2026-11 实测，本机网络环境）：

| 服务 | 地址 | 模型 | 实测 |
|---|---|---|---|
| 智谱 GLM-4-Flash | `https://open.bigmodel.cn/api/paas/v4` | `glm-4-flash` | ✅ 可达，免费 |
| 硅基流动 | `https://api.siliconflow.cn/v1` | `Qwen/Qwen2.5-7B-Instruct` | ✅ 可达，有免费额度 |
| DeepSeek | `https://api.deepseek.com/v1` | `deepseek-chat` | ❌ 本机超时 |
| Google Gemini | `https://generativelanguage.googleapis.com` | — | ❌ 超时 |
| OpenRouter | `https://openrouter.ai/api/v1` | — | ❌ 超时 |
| OpenAI | `https://api.openai.com/v1` | — | ❌ 超时 |

接口是 OpenAI 兼容格式，换供应商只改地址和模型名即可。

**风格怎么保住**：`Persona.kt` 里写死了人设提示词——3~16 字、口语、爱自夸爱斗嘴、
禁止敬语和表情符号、禁止承认自己是 AI，并把她的 30 条真实口头禅当样例塞进去。
模型输出还会过一遍 `sanitize()`：去掉引号、压掉换行、超过 40 字截断、
提到「作为…AI」的直接丢弃。

**不会变哑巴**：Key 没填 / 没网 / 接口报错，全部自动退回本地语料，聊天不中断。
失败原因显示在「学习」面板的「大模型」区块。

**安全提醒**：

- Key 以明文存在应用私有目录 `shared_prefs/llm.xml`，手机 root 或备份能读出来。
  别用主账号的 Key，用完可以在供应商后台删掉重建。
- 开启后每句话都会发到供应商服务器，聊天内容会离开手机。介意就保持关闭。
- 清单里开了 `usesCleartextTraffic`，为了支持局域网自建服务（比如电脑上跑 Ollama）。
  用公网 HTTPS 接口时这个开关不产生额外风险。

**自建/本机模型**（不花钱、不联网）：

```bash
# 电脑上跑 Ollama 后，把模拟器/手机指过去
# 模拟器：adb reverse tcp:11434 tcp:11434，地址填 http://127.0.0.1:11434/v1
# 同一局域网：地址填 http://<电脑IP>:11434/v1，模型名填 qwen2.5:3b
```

## 联网搜索 + 本地知识库（自主搜索学习）

她不会的问题会自己上网查，查到的存进本地知识库，下次直接答。**不需要注册任何搜索服务**。

**流程**：

1. 你问一句 → 先查本地知识库（字符二元组重合度 ≥ 0.55 **且没过期**）
2. 没命中且开着联网 → 先把口语压成搜索词（`Query.toSearchQuery`），再抓 Bing 中国 6 条结果
3. 前 3 条**下载网页正文**：去脚本、去导航/页脚、去 `<ul>/<ol>` 链接列表，留前 900 字
4. 取前 4 条材料（正文优先，正文没有才用摘要）× 500 字，用「查资料模式」回答
5. 查到的存进 `files/knowledge.jsonl`；**「不知道」不存**（存了以后每次问都秒回不知道，看起来就像搜索坏了）

**为什么必须读正文**：早先只拿 Bing 的标题和摘要，一条摘要七八十个字，4 条加起来 300 字，
模型拿这点碎片只能答「不知道」。实测「济南今天天气怎么样」搜回来的是百度百科「济南市」、
济南市政府网、知乎——一条天气都没有。

**实测数据**（模拟器，真连 Bing + 真调 qwen-plus）：

```
问：济南今天天气怎么样
→ 搜索词压成「济南今天天气」（去掉「怎么样」）
→ 命中 6 条，前 3 条抓到正文
→ 模型答：济南今天阴，气温22°C，西南风3级，湿度59%，空气质量优。   （6.5 秒）
→ 再问一次：命中缓存，无请求日志，秒回同一条

问：量子计算机是什么
→ 搜索词压成「量子计算机」
→ 模型答：量子计算机是一类遵循量子力学规律进行高速数学和逻辑运算、存储及处理量子信息的物理装置
```

**开关**：学习 → 接AI → 勾选「联网搜索」。关掉就只用人设 + 模型自身知识。

**查资料模式**（`Persona.researchPrompt()`）和人设模式是两套提示词，**参数也是分开的**：
查资料用 `temperature=0.25, max_tokens=300, readTimeout=45s`，聊天用 `0.95 / 96 / 20s`。
查事实要确定性，原来两处共用 0.95 的温度，等于让模型拿着资料「发挥」。

**知识库有效期**（`Knowledge.ttlFor`）：

| 问题类型 | 有效期 | 例子 |
|---|---|---|
| 时效性 | 1 小时 | 今天、现在、最新、天气、价格、汇率、新闻、比分 |
| 常识性 | 7 天 | 量子计算机、德州在哪 |

没有有效期的话，问过一次天气之后每次问都返回那天的答案，表现出来就是「搜索很差」——
其实它根本没搜，用的是旧缓存。

**数据位置**：`files/knowledge.jsonl`，一行一条 `{"t":时间,"q":问题,"a":答案,"s":["来源",...]}`

**局限（说清楚）**：

- 正文提取靠正则，复杂页面会漏东西：有的站把正文放在 `<li>` 里，会被当成推荐链接剔掉
- **源头不保证新鲜**：Bing 可能返回旧页面，实测天气那条摘要里出现过 2024 年的日期
- 一次问答要 6~10 秒（抓 3 个页面 + 调模型），比纯聊天慢一个量级
- 没做向量检索，靠 bigram 重合度匹配，问法差太远会当成新问题再查一次
- 每条知识只存问答，不存原始网页正文
- 没接 Tavily（免费 1000 次/月，能返回更干净的结果），需要注册，暂时没做

## 上下文记忆（最近 100 条）

回答不是「一句话一问」，模型能看到之前的对话。

- 聊天时把**最近 100 条**对话按 user/assistant 交替放进 `messages`；查资料时只带 20 条，把上下文预算留给材料
- `historyFor()` 会丢掉最后一条：`submit()` 是先 `chatLog.append("我", 这句)` 再调 `askLlm()` 的，
  当前这句已经作为 user 单独传进去了，不丢会重复
- `ChatLog` 本来就是 jsonl 落盘（`files/chatlog.jsonl`），重启不丢，所以上下文能跨次启动

**指代补全**（`Query.withContext`）：问句不足 6 个字时，往前找第一个**带实词**的问句，把关键词拼进搜索词。

```
那空气质量呢  →  空气质量 济南今天天气
```

开头的「那 / 这个 / 还 / 然后 / 所以」会被剥掉。这一步是必须的——实测带着「那」去搜，
Bing 头条结果是汉典的「那 nà、nǎ、nèi、nā」词条，材料全废。

**上文也会写进查资料的 prompt**：光把历史塞进 messages 还不够，
模型看到孤零零一句「那后天呢」，会把它当语法题解释（真出现过：「“那”指代之前提到的事物或时间」）。
所以 `materialPrompt` 会把上一轮问答作为「上文：」一起带上。

**看日志**：

```powershell
adb logcat -s EvilShao:*
# 搜索词=[空气质量 济南今天天气] 命中=6 有正文=3 可用=6 上下文=2条 错误=null
# 模型返回=[...] 错误=[...]
```

**实测**：

```
问：济南今天天气怎么样   → 上下文=0条
问：那空气质量呢         → 上下文=2条，搜索词变成「空气质量 济南今天天气」
```

**局限（说清楚）**：

- 上下文只解决「听懂」，不解决「有料」：材料里没有的事实，模型仍然答「不知道」
- Bing 的结果排序依然一般：搜「空气质量 济南今天天气」，头条是百度百科「空气（地球周围气体）」
- 阿里云免费额度是**每 45 秒 1 条**，高峰期还会 503。现在的错误会翻译成中文
  （「免费额度限流：每 45 秒只能问一次」/「服务端繁忙，过一会儿再问」）显示在学习面板里，
  不再是截断的 JSON，也不会让人误以为「她不想理我」

## 输入框：拼音和输入法

两个坑，都是实测撞出来的。

**1. 没选字的拼音会被当成句子发出去**

雷电模拟器自带的是 `com.android.inputmethod.pinyin`（显示名「雷电输入法」）。它**在点发送之前**
就把字母提交进输入框了，所以点击那一刻：

```
点发送 组词span=-1..-1 文本=[nihao]
```

组词区根本查不到，`input.text` 直接就是拼音。规矩的输入法会留组词区（span ≥ 0），这种能直接判断；
雷电这种只能看内容。

现在的判断：

- 有组词区 → 拦
- 或者：当前是中文输入法（雷电/搜狗/百度/讯飞/AOSP 拼音）**且**内容全是 `a-z` → 拦

拦下来会提示「拼音还没选成字，再点一次就直接发」，**2.5 秒内再点一次就放行**——
万一你就是要发个英文单词，不至于被永久挡住。

`--es ask` 调试入口塞进来的句子用 `debugAsk` 标志跳过这道拦截，否则自动测试全废。

**2. 回答完输入法自己弹回来**

原来只调了 `hideSoftInputFromWindow`，但 `EditText` 还保持着焦点。气泡一出现、布局一变，
输入法就自己弹回来，还会切回默认语言——就是「回答完自动切换输入法」。

现在的做法（第九轮改过一次，见下）：

- 不再「发完就收键盘」：只要输入框有焦点就把键盘留着，接着打下一句不用再点一次；
- 真要收的时候先 `input.clearFocus()`，再延时 80 毫秒收键盘（收了键盘不收焦点会自己弹回）
- `hideKeyboard()` 里顺带 `BaseInputConnection.removeComposingSpans()`，清掉残留的组词状态
- 输入框加 `imeOptions="actionSend|flagNoExtractUi"`（禁掉输入法的全屏抽取编辑器）
- manifest 加 `windowSoftInputMode="adjustResize"`

**实测**：

```
打字 nihao → 点发送      → 拦住，聊天记录条数不变
2.5 秒后再点             → 发出去了
发完 mInputShown=false，她的回复到达后仍然是 false（不弹回）
```

**说明**：打字的时候输入框里还是会看到字母（那是输入法画上去的，应用管不了），
但至少它不会再被当成一句话发到聊天里。

**3. 屏幕底部那条拼音（候选条）**

现象：打字时输入框里空着，拼音却出现在**输入框下方、贴着屏幕底部**，带一条虚线。

实测结论：**那不是应用画的。**

```
dumpsys window windows → InputMethod 窗口 Requested w=1080 h=0   （键盘高度为 0）
dumpsys input_method   → mInputShown=true                        （输入法状态是"显示中"）
uiautomator dump       → 文字始终在输入框内 y 1796-1819（框是 1769-1842）
截图逐行扫描           → 1843 以下暗像素 0 个
```

也就是说：模拟器接了物理键盘，雷电输入法把软键盘折叠了（h=0），
临时用一条小窗口在屏幕底部显示**拼音和候选**。那是你选字用的界面，删掉就打不了中文。
`showSoftInput` 用 `SHOW_FORCED` 也拉不出来，输入法自己拒绝展开。

给了一个开关：**菜单 → 输入法**（存在 `input` 这个 SharedPreferences 的 `noIme` 里）

| 模式 | 底部候选条 | 打中文 |
|---|---|---|
| 系统输入法（默认） | 会出现 | 可以 |
| 关闭输入法 | 不会出现 | 不行，只能直接打英文/数字 |

关掉后实测 `mServedView=null`、`mInputShown=false`，物理键盘照样能输入（`nihao` 正常进框），
而且这时「拼音没选字」的拦截会自动让路——因为打的确实是英文。

想同时要「页面干净 + 能打中文」，正规做法是**让软键盘展开**（雷电侧边栏的键盘按钮），
候选就落在键盘里，不会浮在页面上。

## 学你说话（本地风格适应）

除了学「哪句话她说了效果好」，还会学**你自己是怎么说话的**，然后让自己的回答往你这边靠。
全程离线，数据在 `files/style.json`。

**学什么**：

| 特征 | 怎么判断 |
|---|---|
| 句子长短 | 所有你发的消息的平均字数 |
| 标点习惯 | 一半以上消息不带标点 → 认为你不爱用标点 |
| 感叹号 | 超过三分之一消息带 `！` → 认为你情绪外放 |
| 语气词 | 统计 啊/呀/呢/吧/哈/嘛/哦/咯/嗯/唉/呗/啦/诶，取出现 ≥2 次的最高频 |
| 叠字笑 | 哈哈/嘿嘿/呵呵 出现 ≥2 次 |
| 表情标签 | `[坏笑]` 这类标签出现 ≥2 次 |

**怎么适应**：

1. **本地选句时**（`StyleProfile.adapt`）
   - 你平均 ≤5 字且回复超过 10 字 → 砍到第一个逗号/句号，只留前半句
   - 你不爱用标点 → 去掉句尾的句号
   - 你爱用感叹号 → 有一定概率把句号换成感叹号
   - 你爱打哈哈 → `哈哈` 变 `哈哈哈`
   - 你有高频语气词 → 短句结尾大概率补上那个词（已带语气词的不叠加）
2. **走大模型时**，把风格摘要拼进系统提示词：
   `对方说话很短，多为几个字，基本不用句号，常用语气词「呀、哈」，回应时贴近这个节奏。`

**实测**（模拟器，先灌 10 句「你好啊 / 在哪呢 / 哈哈哈…」这类短句）：

```
学到：平均 2 字，0 句用标点，常用语气词「呀、哈」
连发 8 条消息 → 8 条回复里 0 条以句号结尾
  「噢，笑死我了呀」「我就知道呢」「这我拿手啊」← 自动补了语气词
大模型请求里确认 STYLE_HINT=1（风格提示已注入）
```

**局限（说清楚）**：

- 样本少于 3 句时完全不改，避免瞎模仿
- 只模仿**长度、标点、语气词、叠字**这些表层节奏，不模仿你的用词和话题
- 她原本的短句风格可能被削得更短；不满意就删 `files/style.json` 重置
- 每次训练（每 12 轮对话）会用聊天记录全量重算一次，纠正统计漂移

## 句子打分系统

两套分，各管一件事：**质量分**看句子本身像不像话，**实用分**看这句话说出来效果如何。

### 质量分（0~100，`SentenceScore.kt`）

自己造的句子先过一遍分，低于 55 分的直接丢掉，不再进入候选池。

| 分项 | 权重 | 判据 |
|---|---|---|
| 结构 · 长度 | 18% | 3~6 字满分，7~10 字 90%，11~16 字 70%，17+ 大幅扣 |
| 结构 · 结尾 | 20% | 落在 啊呀呢吧了。！？… 满分，落在实词上只有 40% |
| 结构 · 逗号 | 10% | 0 个 1.0，1 个 0.9，2 个 0.4，3 个以上 0.1 |
| 结构 · 重复 | 7% | 连续三个相同字、或「六的六的六的」这种两字循环，直接 0 |
| 结构 · 字符 | 5% | 出现字母数字直接 0 |
| 新颖度 | 40% | 和已有句子的二元组 Jaccard：≥0.99（复读）0，≥0.85 扣到 0.15，0.35~0.85 最舒服（1.0），<0.35 轻微扣（0.7，可能是拼出来的怪话） |

造句时**一次生成 60 条候选**，全部分完再取前几名入库，而不是"造一条合格就收"。

### 实用分（0~1，`Learner.kt`）

从聊天记录里自动找反馈，七个信号源：

| 信号 | 判据 | 分值 |
|---|---|---|
| 夸奖 | 下一条含 哈哈/厉害/牛/不错/有意思/确实 | +1.0 |
| 嫌弃 | 下一条含 无语/什么鬼/不对/没意思/听不懂 | -1.2 |
| 复读 | 把同一个问题原样再问一遍 | -1.0 |
| 改问 | 下一条和原问题共享 ≥2 个二元组（换着法再问） | -0.6 |
| 追问 | 下一条又是个问句 | -0.3 |
| 冷场 | 下一条只有 1~2 个字 | -0.4 |
| 打哈哈 | 下一条含 哈哈/笑死/6 | +0.8 |
| 继续聊 | 下一条明显比平时长 | +0.5 |
| 接话 | 下一条用了她刚说过的词 | +0.4 |
| 时效 | 1 分钟内回复 +0.3；15 分钟以上 -0.3 | ±0.3 |

单次总信号夹在 [-2, +2]。

**三个关键处理**：

1. **时间衰减**：每条回复的累积分每次 ×0.92，越近的一次影响越大，旧判断会自然淡出。
2. **置信度收缩**：`置信度 = 次数/(次数+3)`，样本少时分自动往 50 靠。看 1 次的分永远保守，看 10 次的分才敢给极端值。
3. **语境分桶**：同一句话分别记在 问句/夸奖/指令/短句/陈述 五个语境下。问她问题时合适的句子，不一定适合跟她斗嘴，采样时按当前输入的语境加权（整体 60% + 语境 40%）。

采样权重：`w = 0.15 + 2.3 × 分数`，自造句再乘质量分 `0.7 + 0.6 × 质量`，另外**12% 概率纯随机**，避免低分句永远没机会翻身。

### 面板怎么读

```
分析过 5 条对话，4 条收到明确反馈。
反馈来源：夸奖 1 · 嫌弃 1 · 复读 1 · 改问 1 · 追问 0 · 冷场 1 · 打哈哈 1 · 继续聊 1

说得好的：
  57分 (1次)  干嘛
被嫌弃的：
  45分 (1次)  你可以闭嘴了
```

括号里是样本次数——只有 1 次的分都挤在 45~57 之间，这是刻意的保守；同一句话说上十几次、反馈一致，分数才会明显拉开。

### 试过但没用的方案（记录一下）

最初想用**字级二元语言模型**给句子打分（用她 95 句语料训一个 bigram LM，算 log 概率）。

结果不可用：`我这么厉害啊` 判 3 分，`哈哈哈，你猜我是傻子吗` 判 84 分——95 句的语料太稀疏，任何一个没见过的二元词组都会被重罚，而"重组"恰恰是她造句的核心。纯 structural + novelty 反而更稳。

## 3D 小猪

现在的小猪是**真的 3D 模型**，不是用球体拼的：149 万三角面、带顶点色，从一张插画生成。

### 模型怎么来的

1. **Meshy 走不通**：账号是免费计划，API 返回 402 ——「Task creation on the free plan is no longer supported」，有 100 积分也没用，必须升级订阅。
2. **改本地跑 TripoSR**：`stabilityai/TripoSR`，单图转 3D，RTX 4060 8G 够用。权重从 hf-mirror 拉（huggingface 被墙）。
3. **两个坑改了源码**：
   - `torchmcubes` 是 CUDA 扩展，Windows 要装 CUDA Toolkit 才能编译 → 换成 `scikit-image` 的 marching cubes，慢几秒但零编译
   - `trimesh 4.0.5` 和 numpy 2.x 不兼容（`ndarray.ptp` 被删）→ 升级 trimesh
4. **构图归一化**：TripoSR 是按「物体占画面 85%、灰底、512×512」训练的。`--no-remove-bg` 会跳过这步预处理，直接喂原图出来是一团泥。所以自己按它的规则做了抠图 + 缩放 + 灰底合成。
5. **颜色是按角度从三视图投上去的**：模型自带顶点色约 40% 是灰的（单图看不到背面）。现在用**正面 / 侧面 / 背面**三张参考图分别投影，每个顶点按自己法线的方位角去对应视角取样：
   - 正面图覆盖 ±85°，背面图覆盖 180°±85°，侧视图只在 ±38° 窗口内说话
   - 侧视窗一开始开得太大，侧脸的颜色会渗到腮帮子上（实测右脸发蓝），收窄后正常
   - 灰底判为「没采到」；画面最底部的暗色是原图的地面阴影也要拒——但瞳孔本来就是暗的，所以「拒暗色」只在画面最下方生效，否则眼睛会被抹掉
6. **清理**：只留最大连通块（去悬空碎片）、砍掉底部水平地面、砍掉灰色地面片、砍掉脚下阴影三角。

### 渲染

`GlbRenderer.kt` + `GlbModel.kt`：自己写的 GLB 解析器，只认 POSITION / NORMAL / TEXCOORD_0 / COLOR_0 / 索引，骨骼和动画直接跳过。

- 顶点色模型不绑贴图，所以初始化时先建一张 1×1 白纹理兜底——不建的话绑定纹理 0，采样全黑，整个屏幕一片黑
- `COLOR_0` 是 `UNSIGNED_BYTE` + `normalized`，读进来要除以 255，否则颜色值 0~255 当 0~1 用，全白
- 模型按包围盒自动缩放到高度 2.85，居中
- 顶点色 + 一盏主光 + 一盏右前补光，保证右脸不掉进阴影

### 情绪：改成整体动作

静态模型没有面部绑定，表情做不了。所以情绪用**整体动作**表达：

| 情绪 | 动作 |
|---|---|
| 平常 | 轻微呼吸起伏 |
| 开心 | 蹦（abs(sin) 做跳跃）+ 挤扁拉长 |
| 惊讶 | 一弹，先放大再回弹 |
| 生气 | 高频小幅抖动 |
| 害羞 | 歪头 + 缩小 |
| 无聊 | 整体下沉、慢慢塌 |

触发逻辑没变，还是按回话里的关键词判断（`moodFor`）。

**这一版丢了什么**：原来那套面部参数（眼睛开合、眉毛角度、嘴角弧度、腮红强度、眨眼）全部失效了。老的自绘版本还在仓库里（`PigRenderer.kt` + `Mesh.kt`），只是 `MainActivity` 现在不用它。

# 对话链路改造（2026-11）

这一版把「聊天为什么慢、为什么答非所问、为什么翻来覆去一句话」逐个拆开重做。
代码仍然是**零第三方依赖**（不引 AndroidX、不引协程），全部用 framework 原生 + JDK 并发类实现。

## 现在的分层

| 文件 | 职责 |
|---|---|
| `MainActivity.kt` | 只做界面：控件绑定、气泡、面板、触摸旋转。业务全部委托出去（原来 1016 行、120 个方法） |
| `ChatBrain.kt` | 对话编排：记忆 → 联网 → 模型 → 本地兜底；单线程队列 + 请求代际（旧请求自动作废） |
| `LlmClient.kt` | OpenAI 兼容接口：**SSE 流式**、失败重试、频率/存在惩罚 |
| `Persona.kt` | 人设提示词 + 研究提示词 + 材料拼装 |
| `ReplyGuard.kt` | 复读检测（字符二元组 Dice 相似度）、按句末标点截断 |
| `HistoryBudget.kt` | 按字符预算裁上下文（替换固定 100 条） |
| `ReplyText.kt` | 输出清洗（去引号、挡「作为 AI」这类崩人设的话） |
| `MoodClassifier.kt` | 从回复内容推表情 |
| `Query.kt` | 搜索词压缩、上文补全、**该不该联网** |

## 改了什么，为什么

| 现象 | 根因 | 改法 | 实测 |
|---|---|---|---|
| 回复要等 20~90 秒才冒出来 | 同步等整段回复；正文串行抓 3 篇（最坏 3×13 秒） | `chatStream()` 走 SSE 边收边显示；`enrichParallel()` 三条线程同时抓 | 首个字 1~3 秒出现；单次回复 16 个增量块 |
| 连发两句，回答对不上问题 | 每次提问开一个裸 `Thread`，谁先返回谁先说 | 单线程队列 + `generation` 计数，旧请求结果直接丢弃 | 连发只认最后一句 |
| 免费额度一 429 就突然变成语录 | 失败没有重试 | 429/5xx/超时退避重试一次；确认限流后**立刻**回本地，不再白等两次超时 | 限流场景 19.9 秒 → 13 秒内有回应 |
| 连着好几轮说同一句话 | 只在提示词里写「别重复」 | `frequency_penalty` / `presence_penalty` + 最近 8 句硬比对 + 进程启动时用聊天记录预热 | 撞车时自动换一句 |
| 问「你是谁」被答成韩剧，还被存进知识库 | 联网前没有「该不该搜」的判断 | `Query.worthSearching()`：问她本人、寒暄、撒娇不联网；缓存也只服务事实类问题 | 「你是谁」走人设，不再搜索 |
| 搜索词被上一句污染（`你是谁 hello`） | 补上文只看句长 | 只有出现指代词（那/它/这个/还/然后…）才借上文，且跳过英文寒暄 | 搜索词回到 `你是谁` |
| 长答案被切在半个词上 | `s.take(maxLen)` | 按句末标点截断（`ReplyGuard.fitToSentence`） | 断句完整 |
| 聊久了上下文可能超模型上限 | 固定带 100 条 | 字符预算 1200，至少保留最近两轮 | 长对话不再爆上下文 |
| 缓存命中要等 3.5~20 秒 | 命中后还让模型「用她的口吻重说一遍」 | 命中直接秒回，本地零网络 | **17ms**，且不再被 `style.adapt` 砍掉事实半句 |
| Activity 销毁后回调还在跑 | `Thread` + `Handler` 无生命周期 | `onDestroy` 关闭编排层，代际自增作废在途请求 | 不再有回调打到已销毁界面 |

## 已知取舍

- 免 Key 的公共接口（Pollinations）高峰期经常 429，查资料读超时压到 10 秒，超时就退直答；
  换成自己的 Key（智谱 GLM-4-Flash 免费额度）会明显更稳，超时放宽到 30 秒。
- 复读检测是进程内的，进程重启靠聊天记录预热最近 8 句；跨设备没有共享。
- 知识库仍是 append-only 的 jsonl，条目多了检索会变慢（几万条以内无感）；
  真要做大得换倒排索引，目前没必要。

## 第二轮：把「没条理」修掉（同日）

第一轮只解决了「快」，用户反馈：**回得快了，但答得驴唇不对马嘴**。查下来有三层原因。

### 原因一：全新安装默认没接大模型，所有回答都是随机语录

`LlmClient.enabled` 默认 `false`，装完就是纯语录模式。而语录引擎在关键词对不上时
会从「签名 / 自造句」里随机抽一句 —— 于是：

```
我：你好      →  她：瞎说
我：？        →  她：谁跟你一样
我：你在说啥  →  她：呵呵，我真是服了
```

每句都跟她要回的那句话无关，连起来就是精神分裂。

**改法**
- 默认打开免 Key 的公开接口（`keyless = true`），装完就能真的对话；
  想纯离线可以在面板里关掉「启用大模型」。
- 离线模式下不再随机：关键词规则命中才用规则回复，否则给一句**接得住这句话**的短应答
  （问句 → 「……我这会儿查不了」；闲聊 → 「嗯」「……哦」）。
  想听她随口吐槽，点她本人仍然是随机签名。

### 原因二：一个问题最多打 4 次模型请求，把免费额度打爆

第一版的链路是「记忆 → 查资料 → 直答 → 复读重试」。免费接口 45 秒 1 条，
4 次请求必然 429，于是绝大多数问题都掉进兜底——**快，但全是废话**。

**改法**：一次提问最多一次模型请求。查资料成功即结束；失败且不是限流才允许一次直答补救；
复读不再重打，改成提示词里点出最近 3 句（重复一句切题的，好过换一句不着边际的）。

### 原因三：接不上上文、资料不切题

| 现象 | 根因 | 改法 |
|---|---|---|
| 「那明天呢」搜成了「明天」，答出南方天气 | 判断「有没有指代」用的是已经去掉「那」的搜索词 | `withContext()` 改看**原话**，搜索词变成 `明天 济南今天天气` |
| 问济南天气，喂进去的资料是「南方阴雨」 | 搜索结果的正文没做相关性过滤 | 从搜索词抽实词（`济南`），资料里不含实词的整条丢掉；一条都不含就**跳过查资料**，退成凭印象直答 |
| 模型直接编「明天南方将出现大范围阴雨」 | 小模型爱补全 | 人设加硬规则：不知道未来的事就说不知道，**绝对不许编**；问到家在哪答山东德州，别改籍贯 |
| 问「谁是邵珠佳」去网上搜同名路人 | 只要不是寒暄就去搜 | `SELF_NAME` 命中（邵珠佳/Whisper/小猪）一律不搜、不吃缓存 |

### 改完的实测对话（雷电14 + 免 Key 接口）

```
我：你好              →  哈哈哈，怎么啦？                      (MODEL, 2.8s)
我：你是谁            →  我叫邵珠佳，班团支书。                  (MODEL, 2.8s)
我：济南今天天气怎么样  →  今天济南中东部大部气温回升。            (SEARCH, 4.7s)
我：那明天呢          →  明天阴雨绵延。                        (MODEL, 4.0s)
```

搜索那两行的日志：

```
搜索词=[济南今天天气] 实词=[济南] 命中=6 切题=6 有正文=3
搜索词=[明天 济南今天天气] 实词=[济南] 命中=6 切题=0
资料都不切题，跳过查资料
```

### 已知限制

- 免 Key 的 Pollinations 是公共免费接口，模型本身弱、高峰期限流，**还是会编**（上面「明天阴雨绵延」就是编的）。
  想真的靠谱得填自己的 Key：智谱 GLM-4-Flash 免费额度就够，改动只有设置面板里三行。
- 未来类问题（明天天气、比分）靠一次搜索本来就不可靠，现在至少不会拿别的城市的稿子冒充答案。

## 第三轮：给小猪减面（26 万面 → 6.5 万面）

上一版把对话修顺了，这一版动模型。先看体检结果：

| 项 | 改之前 | 说明 |
|---|---|---|
| 文件 | 4.99 MB | 一个 GLB 里全是几何数据，没有贴图 |
| 三角形 | 260,408 | 手机 GLES2 单 pass，每帧搬 78 万个索引 |
| 顶点 | 131,536 | 超过 65535，索引只能 32 位 |
| 索引块 | 2.98 MB | 占整个文件 **60%**，就因为顶点数超标 |

三件事一起做，改完：

| 项 | 改之后 | 变化 |
|---|---|---|
| 文件 | **0.88 MB** | −82% |
| 三角形 | **64,999** | −75% |
| 顶点 | **32,941** | −75% |
| 索引 | **uint16** | 索引块 2.98 MB → 0.39 MB |
| gzip 后 | 1912 KB → **725 KB** | −62% |
| APK | 2.94 MB → **1.65 MB** | −44%（其余是 dex） |

### 怎么减的

用 GitHub 上的 **meshoptimizer**（`zeux/meshoptimizer`）——Python 侧是它的封装
`fast-simplification`，算法和 `gltfpack -si` 是同一套：二次误差度量（QEM）边折叠，
`agg` 控制锐边保留。脚本在 `tools/optimize_pig.py`：

```bash
python tools/optimize_pig.py --in pig.glb --out pig-opt.glb --tris 65000
python tools/optimize_pig.py --tris 26000 --agg 10     # 更狠，更糙
```

流程：读 GLB → 焊接重复顶点（这个模型导出时已经焊好，所以这步没合掉东西）→
QEM 减面 → **颜色就近转移**（减面后顶点位置变了，按最近原始顶点取色）→ 重写 GLB，
顶点数降到 65535 以下后索引自动切 16 位。

### 为什么不用 Draco / meshopt 压缩

`GlbModel.kt` 是手写的极简加载器，只认 POSITION / NORMAL / TEXCOORD_0 / COLOR_0 /
索引 / 内嵌贴图。上 `EXT_meshopt_compression` 或 Draco 就得再塞一个解码器进 APK，
为了省几百 KB 不值得；`KHR_mesh_quantization` 也不行——它靠节点变换还原真实尺寸，
而我们的加载器不看节点。所以只做**无损的格式调整 + 减面**，加载器一行没改。

### 怎么验证没减坏

三条独立的证据，都在 `tools/render_glb.py` 里能复现：

| 检查 | 结果 |
|---|---|
| 表面积总和 | 1.7972 → 1.7892，**−0.45%** |
| 双向 Chamfer 距离（相对包围盒对角线） | 平均 **0.29%** / P99 0.89% / 最大 3.68%（在耳朵边缘） |
| 软渲染轮廓 IoU（正交前视，1040×1280） | **0.9973** |
| 同区域平均色差 | 8.7 / 255（3.4%，来自颜色就近转移） |

`render_glb.py` 是自己写的软光栅（正交投影 + z-buffer + 朗伯光照），
只依赖 numpy 和 Pillow，不装 trimesh/open3d 也能跑：

```bash
python tools/render_glb.py     # 输出 render-old.png / render-new.png 并打印 IoU
```

### 后续：颜色、法线、再减一半

用户反馈「颜色太不鲜艳、建模再优化一下、流畅一点」。查下来最要命的**不是颜色数值，是模型没有法线**：

`COLOR_0` 里的色本来就只有 0.30 的平均饱和度，而 `pig.glb` 连 `NORMAL` 都没有。
`GlbRenderer` 发现没法线，就给全体顶点塞 `(0,0,1)` —— 于是整只猪的法线完全一致，
光照算出来是个常数，等于**平面着色**：没有体积、没有明暗过渡，颜色再艳也发灰。

四处一起改：

| 改动 | 之前 | 之后 |
|---|---|---|
| 顶点法线 | 无（加载器补 (0,0,1)） | 减面后按面积加权烘焙平滑法线 |
| 顶点色 | 饱和度 0.30 | 0.51（vibrance：越灰提得越多，纯色不爆） |
| 着色器饱和 | `mix(lum, base, 1.22)` | `1.55`，对比 1.08 → 1.12 |
| 环境光 | `0.60 + 0.46*diff` | `0.70 + 0.42*diff`（有真法线后背光面别闷死） |
| 三角形 | 64,999 | **31,998** |
| 文件 | 0.88 MB | **0.62 MB** |
| 索引 | 32 位 | GLB 里 16 位；渲染器按顶点数**自动**选 16/32 位上传 |

注意最后一条：`GlbRenderer` 原来写死 `GL_UNSIGNED_INT`，因为它总是把索引转成 IntBuffer 上传。
现在顶点数 ≤ 65535 时上传 `ShortBuffer` 并用 `GL_UNSIGNED_SHORT` 绘制，索引带宽直接减半。

实测（雷电14，1:1 截图取样）：

| 指标 | 改前 | 改后 |
|---|---|---|
| 小猪区域平均饱和度 | 0.397 | **0.714**（+80%） |
| 平均明度 | 0.320 | 0.350 |
| 帧 P50 / P95 | 8.3 / 16.7 ms | 8.3 / **8.3 ms** |

模拟器跑在 120Hz vsync 上，P50 都顶到 8.3ms，看不出差距；P95 从 16.7ms 收到 8.3ms 说明长帧没了。
真机上 3.2 万面 + 16 位索引的收益会比这里明显。

生图命令：

```bash
python tools/optimize_pig.py --in pig-opt.glb --tris 32000 --agg 6 \
       --sat 2.0 --val 1.06 --contrast 1.10 --out pig-vivid.glb
```

三档颜色（`sat` 0.29 / 0.50 / 0.73）的对比图见 `color-compare3.png`。
嫌不够艳可以把 `--sat` 提到 3.0 重出，一条命令的事。

### 第四轮：手脚保精度 + 精致渲染

用户反馈「改一改脚的精度，还有手的，精致的渲染一下」。

查下来问题很直接：全局 QEM 是按「误差 / 面积」决定塌哪条边的，手脚面积占比小，
所以先被抹平。同一个保护区域（两侧外缘球 + 最低 0.10 层）里：

| | 总面数 | 手脚区面数 | 手脚区误差 |
|---|---|---|---|
| 原始模型 | 260,408 | 21,031 | — |
| 全局减面 | 31,998 | **2,788**（丢掉 87%） | 0.40% |
| 分区减面 | 36,030 | **21,031**（一个没丢） | **0.136%** |

**做法（`tools/detail_pig.py`）**

1. 切两张皮：手（两侧最外侧球，半径 0.13）∪ 脚（最低 0.10 层）一个面都不减；
   其余 23.9 万面减到 1.5 万。
2. 接缝靠 meshoptimizer 的 `preserve_border=True`：身体那半的切边顶点被锁住不动，
   手脚那半本来就是原始顶点，两边坐标逐位相同，按坐标焊接就严丝合缝。
3. 验证：开放边 2,508 条，和原始模型**完全一致** —— 说明分区没有引入任何新裂缝
   （这模型本来就不是水密的，那 2,508 条是 Meshit 生成的原始洞）。

**渲染（`GlbRenderer` / `MainActivity`）**

| 改动 | 说明 |
|---|---|
| 4x MSAA | `GLSurfaceView` 默认配置一定没多重采样，自己写了 `MsaaChooser` 挑 EGLConfig；拿不到就退回普通配置。日志实测 `EGL: 4x MSAA 已启用` |
| 半球环境光 | 头顶冷、脚下暖，`0.50~0.78` 两色插值，代替原来的单一环境光常数 |
| 高光 | Blinn 近似，指数 26、强度 0.16，鼻尖/耳缘有亮点 |
| 亮度回补 | 新光照一开始把明度压到 0.27（发闷），加了 0.38 基础项回到 0.355 |

实测（雷电14 截图取样）：明度 0.350 → **0.355**，饱和度 0.714 → 0.697（半球光掺了一点灰），
MSAA 由日志确认开启。局部（脚 + 左手）放大对比见 `hands-feet-compare.png`。

生图命令：

```bash
python tools/detail_pig.py --in pig-orig.glb --out pig-detail.glb \
       --body-tris 15000 --hand-r 0.13 --foot-y 0.10 --sat 2.0
```

### 第五轮：给脚穿鞋（脚不画了）

前一轮把脚做得越来越精细，方向是错的 —— 脚趾是几十个小突起，低模里必然糊，
留着脚就永远要在「糊」和「面数」之间打架。用户给的方向更对：**穿鞋，把脚盖住**。

**做法（`tools/shoes_pig.py`）**

1. 切脚：重心低于 `y_min + 0.12` 的面全删（7,021 面，19.5%）。
2. 造鞋：icosphere（二十面体细分球，思路同 GitHub `mikedh/trimesh` 的 `creation.icosphere()`）
   先按 `|v|^0.5` 推成超椭球 —— 方圆的鞋型，截面到顶部仍然宽，
   椭圆鞋在 3/4 高度处会收窄，切口就露出来了。
   再沿轴缩放、平底（y 下钳）、脚尖收窄上台。
3. 尺寸按**切面那一圈**量，不是按脚印（脚印比脚踝细，按脚印做必然露腿）。
4. 自动校验：用超椭球隐式方程 `Σ|p_i/a_i|^(2/e) ≤ 1` 逐个验算切口环的 166 个点，
   包不住就把鞋放大 6% 重造，最多 6 次（这次第 1 次就 100% 了）。
5. 补盖：给切口补一个扇形盖（在鞋里，看不见）。就算鞋差一点，也不会露出空洞。

**结果**

| | 上一版（细脚） | 这一版（穿鞋） |
|---|---|---|
| 三角形 | 36,030 | **31,735**（少 4.3k） |
| 文件 | 0.72 MB | **0.50 MB** |
| APK | 1.61 MB | **1.27 MB** |
| 切口环覆盖 | — | **100%**（166 点全包住） |
| app 截图棕色像素 | 83,538 | **128,361**（+54%；下半屏 +86%） |

鞋的最后尺寸：宽 0.26 × 长 0.43 × 高 0.18；鞋底米白、鞋面深棕、鞋口一圈深色滚边。

生图命令：

```bash
python tools/shoes_pig.py --in pig-detail.glb --out pig-shoe.glb \
       --cut-y 0.12 --height 0.18 --boxy 0.5
```

### 第六轮：雷霆大拖鞋

用户要的是「雷霆大拖鞋」，不是精致运动鞋。之前一直往「把脚做细」的方向修，方向错了。

**关键发现**：切到 0.12 高时，切口是**一道连在一起的口**（两只脚踝以下并成一体，166 个点的单环）。
按左右做两只鞋是错的 —— 两只平台在中间叠在一起，糊成一坨。改成**一只大拖鞋**把两只脚一起装进去。

**做法**
- 切脚：重心低于 `y_min+0.12` 的面全删（7,021 面）
- 大底：超椭球压扁成厚平台，0.54 宽 × 0.45 长 × **0.26 厚**（猪高 1.03，鞋占 1/4，够「雷霆」）
- 配色按高度分层：黑大底 <18% / 米白中底 18–70% / 亮黄一圈 70–80% / 红鞋口 80–87% / 米白垫面 >87%
- 两侧各贴一枚黄色闪电（薄片几何，不是贴图）

**踩过的坑**
1. 绑带用半圆拱做，半径=鞋宽，在 0.26 高度正好绕过肚子 —— 等于给猪系了条腰带。删掉，改成鞋口一圈红边（纯染色，不加几何）。
2. 尺寸按「0.1 以下所有点」量会把肚子算进去，鞋底直接做到 0.6 长；改成按**切口环**量。
3. 闪电是凹多边形，扇形三角化会自交；改成「中心线 + 半宽」生成带状网格。

**结果**：30,467 面、0.48 MB、APK 1.26 MB，切口环 166/166 全埋在底里。

#### 第七轮修正：鞋一直没画出来（索引偏移）

两处 `--dump` 自检终于暴露了问题：鞋做好了、颜色也写进 GLB 了，但**渲染里根本没有鞋**。

原因：造鞋时顶点是拼在身体后面的，索引却从 0 开始算，于是所有鞋面都指到身体顶点上，
看上去就是「没穿鞋」。`shoes_pig.py` 踩过一次，`slipper_pig.py` 复制粘贴时又踩了一次。

现在脚本里加了不变量检查，出包前直接打印：

```
引用鞋顶点的面: 1,492（3 组；为 0 就是索引偏移错了）
```

**怎么验证「到底画出来没有」**：模拟器 `screencap` 抓不到 GLSurfaceView 的内容
（截出来是窗口底色，不是渲染器的粉色 clearColor）。所以在 `GlbRenderer` 里加了

按 58×46 采样，把像素按颜色分类打成字符图写进 logcat。这才看到「鞋不存在」。

**另外**：大拖鞋的尺寸改成按「切面以上那一段身体」量，鞋做成 0.75×0.71×0.30——
把整个下半身罩住；之前按切口环量，鞋比脚细，脚会从鞋帮外面露出来。

### 第七轮：说话带刺——夸别人就阴阳，高兴了自称「朕」

### 第九轮：打字顺手一点

用户反馈「输入汉字很困难」。查下来是两件事叠在一起：

1. **发完就收键盘**：每发一句都得重新点输入框，输入法还要重新绑一次（模拟器上经常绑不上）；
2. **模拟器的候选条压在输入框上**：物理键盘在，输入法把软键盘折叠成高度 0，
   候选条浮在屏幕最底部，正好盖住输入框和「说」。

改法：

- 发完不再收键盘：输入框有焦点就把键盘留着，接着打下一句；
  真要收时才 `clearFocus` + 延时收键盘（不放开焦点会自己弹回）。
- 输入框自动上移：`WindowInsets.Type.ime()` 报出的键盘高度 < 80dp 时（模拟器候选条场景），
  整条输入栏上移 112dp；真机软键盘展开时不动，避免和 resize 打架。
- 长按「说」= 把剪贴板里的整句直接发出去。电脑上把话打好复制，模拟器剪贴板是通的。
- 「拼音还没选成字」的提示补一句「急的话长按说粘贴发送」。

**实测**（模拟器）：点输入框后输入框 y 从 1769 抬到 1573；发完 `mInputShown=true`、
焦点还在、能直接接着打；长按「说」把剪贴板里的 `paste` 发了出去。

**限制**：模拟器输入法窗口高度是 0（`Requested w=1080 h=0`），`SHOW_FORCED` 也拉不展开，
这是 ROM 这边的事，应用改不了。想在模拟器里正常打中文，要么长按「说」粘贴，
要么在雷电侧边栏把软键盘展开；手机上没这个问题。

### 第十三轮：接百炼（阿里云）的 deepseek-v4.1-flash

用户选的接口：阿里云百炼 compatible-mode，模型 `deepseek-v4.1-flash-1017`。
它带思维链：不关的话思考过程会把 max_tokens 吃光，正文是空的
（实测 max_tokens=60 时 `content=""`，额度全花在 reasoning 上）。

做法：

- `LlmProviders.needsNoThinking(base, model)`：百炼地址、或者 `deepseek-v4` 开头的模型，
  请求体里自动加 `enable_thinking: false`；别的接口不发这个字段
- 设置页加「用百炼（DeepSeek）」按钮，一键填地址和模型，Key 自己粘
- 请求日志加一行「请求接口：标签 · 模型」，以后一眼看出这句话是谁回的
- **Key 只写在这台设备的 SharedPreferences 里，不进代码、不进仓库**
  （仓库是公开的，硬编码等于把额度送人）

实测（模拟器，流式）：`在吗，今天好累` → 「累就歇着，朕准了。」3.9 秒，
日志 `请求接口：当前设置 · deepseek-v4.1-flash-1017`；关掉思维链后首字 0.5 秒。

换设备时：设置 → 接入大模型 → 点「用百炼（DeepSeek）」→ 粘 Key → 保存。
